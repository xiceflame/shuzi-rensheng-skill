# 首次初始化（Bootstrap）—— 把空库变成「有内容的系统」

> **这是 setup 里最重的一步**：前面几步只是「配置」，这一步是**真正把数据灌进去、把图谱建出来**。
>
> ⚠️ **必须单独成为一步**，因为它：
> - **耗时长**（几小时，不是几分钟）
> - **花钱多**（一次性几百元量级）
> - **必须用 API 或高性能 GPU**（本地弱机器几天跑不完）
>
> **只做一次**。之后靠日常增量维护。

---

## 一、它在流程里的位置

```
第 0 步 探环境 + Agent 自我识别     （自动）
第 1 步 建知识库骨架                ✅ 必需
第 2 步 定性能架构 + 配 API          ⭕
第 3 步 配采集端 + ★首次全量导出      ⭕   ← 数据到手
第 4 步 ★★ 首次初始化（回填 + 建图谱） ⭕   ← 本文，最耗资源
第 5 步 配提醒渠道                   ⭕
第 6 步 配定时（日常增量）            ⭕
第 7 步 验收                        ✅ 必需
```

**必须在「配定时」之前做** —— 否则定时任务会从空库开始，产出也是空的。

---

## 二、数据从哪来（两类）

### A. 微信数据（首次必然要接）
```
① 采集端解密导出（全量，不是增量）
   ~/wechat-export/
     ├── text/         全量历史（2018 至今，2266 会话 / 327 万条）
     ├── focus/        关注会话文字
     ├── focus-voice/  语音（SILK → mp3）
     ├── focus-images/ 图片（.dat → png/jpg）
     ├── focus-media/  群里的 PDF/Office/音频
     └── focus-money/  转账/红包

② 语音转写    （本地/API，见 speech-to-text.md）
③ 附件处理    （抽文本 → 去重 → OCR，见 attachments-ocr.md）
④ 抽成可检索的月度 md（searchable/）
```

### B. 其他数据源（Work Buddy / 邮件 / Notion / 手工资料…）
**统一处理方式**：**导入到 `raw/`，走同一套流程**

```
<你的数据> → 复制进 <vault>/raw/<分类>/
             ├── raw/chat/claude/      Claude 对话导出
             ├── raw/chat/chatgpt/     ChatGPT 导出
             ├── raw/docs/             文档/PDF/表格
             ├── raw/screenshots/      截图
             ├── raw/handwritten/      手写照片
             └── raw/misc/             其他

→ 电子文档：本地抽文本（免费）
→ 扫描件/图片：本地 OCR 或服务器 OCR
→ 纯文本导出：直接进提炼
```

> **Work Buddy 这类桌面工作端**：如果它能**导出数据**，就导出成文件丢进 `raw/`；
> 如果它只提供 **API**，写个小脚本拉取后落盘到 `raw/`。
> **关键：只要变成「文件」，就进了同一套流水线**——不需要为每个数据源单独设计。

## 三、四个阶段（按算力需求递增）

### 阶段 1 · 本地免费（可在弱机器上跑）
| 做什么 | 工具 | 成本 |
|---|---|---|
| 去重（内容 sha256） | `media_dedupe.py` | 0 |
| 电子文档抽文本 | `media_extract.py` | 0 |
| 本地 OCR（扫描件） | `ocr_vision.py`（系统 OCR） | 0 |
| 语音转写（短片） | `transcribe_voice.py` | 0 |
| 加密数据解密 | 采集端脚本 | 0 |
| **图片解码** | 采集端脚本 | 0 |

> ✅ **这一层先把「免费的都做完」** —— 能省掉后面一大半的 API 用量。

### 阶段 2 · 需要算力（本地 GPU 或 API）
| 做什么 | 本地够（≥8GB） | 不够则 |
|---|---|---|
| 语音转写（长音频批量） | faster-whisper + VAD | ASR API |
| 向量嵌入（全量） | 本地 Ollama Qwen3-4B | embedding API |
| 重排（可选） | 本地 reranker | 不部署 |

### 阶段 3 · 需要大 LLM（**必须 API**）
**这是最花钱的一步** —— 把原始数据**提炼成知识库页面**：
```
原始聊天/文档  →  LLM 提炼  →  wiki/projects/  ·  wiki/people/  ·  wiki/journal/
```
- 分批跑（按会话 / 按月份）
- **优先空闲时段**（有峰谷价的服务便宜一半）
- 见 `cost.md` 估算

### 阶段 4 · 建图谱（本地免费）
```
① 补内链：项目 ↔ 人物 ↔ 当天 ↔ 会话
② 修孤岛 / 断链
③ 建汇总层（monthly/quarterly）
④ 重建向量索引
```
用 `lint` 与 `rollup` 工作流。

## 四、⚠️ 为什么必须「批量用 API/GPU」

| | 本地弱机器 | API / GPU |
|---|---|---|
| 语音转写 17h 音频 | **3.8 小时** | **20–40 分钟** |
| 全量嵌入 | 几小时 | 十几分钟 |
| 提炼 15 个月聊天 | 本地小模型**质量差**且慢 | 几十分钟 |

> **在弱机器上做首次回填 = 几天。** 这是本系统唯一「必须借算力」的环节。

## 五、给 agent 的执行清单

**开始前先跟用户确认**：
1. 「数据在哪个机器上？」（采集端 vs 本机）
2. 「机器是什么配置？」（看 `gpu_tier`）
3. 「预计要处理多久的历史？」（几个月/几年）

**然后按阶段推进，每阶段报一次进度**：

```
✅ 阶段 1（本地免费）：去重 X 份 / 抽文本 Y 份 / OCR Z 件 / 转写 N 条
✅ 阶段 2（算力）：嵌入 M 个 chunk（用时 T）
⏳ 阶段 3（LLM 提炼）：已处理 A/B 个会话…   ← 最慢，要报进度
✅ 阶段 4（建图谱）：补内链 X 处 / 修孤岛 Y 个 / 建汇总 Z 页
```

**中途失败了怎么办**：**每阶段可断点续跑**（都有 `.transcribed.tsv` / `_manifest.tsv` 之类的进度文件），
不用从头再来。

## 七、之后就不需要它了

首次初始化**只做一次**。之后：
- 每 4h：增量采集 + 转写 + 建索引（**本地免费**）
- 每天 1–2 次：增量整理（**LLM API**，几分钟）
- 每月：月汇总

> **首次是「一次性大投入」，日常是「细水长流」。** 这正是 [`performance-tiering.md`] 讲的
> 「增量与批量分开」在初始化场景的体现。

## 八、并发策略（大批量提速的关键）

回填的瓶颈不在算力，在**串行等待**。三个阶段都能并发：

### 8.1 向量嵌入 → API 异步并发
- 单条调用 → 一条等一条，慢
- **批量提交 + 异步**（不等回包继续发下一条）→ **数倍提速**
- 本地 Ollama 也支持并发请求（`OLLAMA_NUM_PARALLEL`），但受显存限制

### 8.2 LLM 提炼 → **按月份片，每片一个 agent/thread**
```
thread 1 → 2025-01 的全部会话   ┐
thread 2 → 2025-02 的全部会话   ├ 互不干扰
thread 3 → 2025-03 的全部会话   │ 各写各的月份
…                               ┘
```
**为什么按月切**：
- 每个月的数据**自成一片**（会话按月归档）
- 写入的是**不同文件**（`journal/2025-01-*.md` 等）→ **不会冲突**
- 单月失败不影响其他月 → **可断点续跑**

> ⚠️ 别按「会话」切 —— 同一个会话跨多月，两个 thread 会写同一个人的档案页 → 冲突。
> **按月切最安全**（本系统的 journal 本来就是按天的，天然按月分组）。

### 8.3 语音转写 → 多进程 + GPU
- 按**文件**切分给多个进程
- 有 GPU 时用 faster-whisper（每个进程独占一部分显存，注意别超）

### 8.4 并发度怎么定
| 资源 | 建议 |
|---|---|
| LLM API | 看服务商的**并发限制**，一般 4–8 安全 |
| 嵌入 API | 同上 |
| 本地 GPU | 按显存算：并发数 × 单模型显存 ≤ 总显存 |

## 九、⚠️ 解密阶段必须有人盯着

**整个流程里，只有「解密与导入」这一段不能无人值守。**

| 可能出的事 | 现象 | 补救 |
|---|---|---|
| 密钥扫描不到 | 「密钥 0 个」 | 确认微信在运行且已登录；重跑只读扫描 |
| 微信崩溃 | 微信闪退 | **别用 lldb 断点**（本就会崩）；重启重来 |
| 某分片缺密钥 | **某段时间整段没消息** | 按分片年表排查，单独补扫 |
| 权限被拒 | `Operation not permitted` | 检查 FDA / Terminal 中继 |
| 弹授权框卡住 | 卡住等点击 | 走 Terminal 中继，人点一下 |

**所以**：
- **解密阶段** → 告诉用户「我在盯着，可能需要你配合（点授权/重启微信），出问题有补救方案」
- **解密完成、数据落盘后** → 后面的回填**可以无人值守、可并发**，用户可以去干别的

**解密完成的标志**：`~/wechat-export/` 各目录都有产物（见 `wechat-pipeline.md`）。

## 十、估算要基于「用户阐述的范围」

**不要机械按全量算**。先让用户用自然语言说清楚：
1. **关注的会话**（哪些人/群）
2. **关注的方向**（工作/家庭/某项目）
3. **截止到什么时候**（近一年 / 全部）

然后：
```bash
bash setup/estimate.sh --convs 8 --months 12 --parallel 4
```

> **实测差距**：全量（28 会话 / 3 年）≈ **7.5 小时**；
> 只看 **8 个会话 / 近 12 个月** → **13 分钟**。**差 35 倍。**

这就是为什么「先问清楚」是启动前**必做**的一步。
