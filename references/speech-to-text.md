# 语音转写（短片增量 vs 长音频批量）

> **核心认知**：语音转写有**两种完全不同的场景**，用同一套方法会吃大亏。
> 搞混了，就会出现「日常几分钟」vs「回填几小时」的巨大差异。

---

## 一、两种场景（必须先分清）

| | **A. 短片增量**（如微信语音） | **B. 长音频批量**（如会议/演出/录音） |
|---|---|---|
| 形态 | 海量**超短片**：中位 **6.9 秒**、均值 10 秒、上限 60 秒 | **长文件**：单体几分钟，可达数小时 |
| 数量 | 数千个片段，但**每轮只新增几条** | 成百上千个文件，**一次全量** |
| 典型来源 | 微信语音（微信本身限长 60s） | 群里的录音/会议/演出/家庭录音 |
| **处理方式** | ✅ **本地小模型 + 增量 + 批处理** | ⚠️ **GPU + faster-whisper + VAD** |
| 耗时 | **几十秒 ~ 几分钟** | 本地 CPU 要**几小时**（不可接受） |

> **实测对比**：7565 个微信短片（增量）几十秒跑完；
> 211 个长音频（17 小时）用 `openai-whisper` 本地要 **3.8 小时**。

---

## 二、短片增量：怎么做对

**三个要点**（缺一不可）：

1. **增量**：只处理新到的（用 `.transcribed.tsv` 记录已处理）
2. **批处理**：**模型只加载一次**（`load_model` 放在循环外，不是每文件加载）
   > ⚠️ 这是最容易犯的错——每文件加载模型会让耗时翻几十倍
3. **小模型够用**：`base` ≈ 4–8× 实时，短片场景完全够

**调度**：每 4 小时一轮（跟着数据刷新走）

```python
model = whisper.load_model("base")     # ★ 循环外，只加载一次
for f in new_files:
    result = model.transcribe(f)
```

## 三、长音频批量：四个提速杠杆

| 杠杆 | 做法 | 提速 |
|---|---|---|
| **① 换引擎** | `faster-whisper`（CTranslate2）替代 `openai-whisper` | **4–8×（CPU）** |
| | Apple Silicon 用 **`mlx-whisper`**（M4 上极快） | 🔥 |
| **② 上 GPU** | `faster-whisper large-v3` + CUDA | **几十倍** |
| | 实测：17 小时音频 → **~20–40 分钟**（还能用 large 更准） | |
| **③ VAD 过滤** | 先跑 **`silero-VAD` / `webrtcvad`** 做人声检测 | 省一大半 |
| | **音乐/静音段落直接跳过**（转了也是乱码） | |
| **④ 分级 + 并行** | 增量用 `tiny`/`base`；回填用 `large-v3`；按文件**多进程并行** | 🔥 |

> **业内惯例**：短片增量走本地小模型；**长音频/批量一律上 GPU + faster-whisper + VAD**，
> 不再用 `openai-whisper`。

### 引擎选型

> 一键本机安装：`bash setup/local-models.sh`（按平台自动选 mlx-whisper / faster-whisper，全离线免费）。

| 引擎 | 适用 | 说明 |
|---|---|---|
| `openai-whisper` | 短片增量（现状） | 慢，但够用 |
| **`faster-whisper`** | **长音频/批量** | CTranslate2，CPU 也快 4–8× |
| **`mlx-whisper`** | **Apple Silicon** | M 系列原生加速 |
| ASR API | 没显卡时的批量 | 按音频分钟计费，见 `models-as-api.md` |

## 四、⚠️ 音乐/演出音频的特殊规则（重要）

**whisper 对非语音会输出乱码**（歌词听不清就编，纯音乐更是胡言乱语）。

**规则**：
| 音频类型 | 处理 |
|---|---|
| **语音**（对话/会议/汇报） | ✅ 正常转写 → 进提炼流程 |
| **音乐 / 排练 / 演出** | ⚠️ **只记元信息**（「这是哪场/哪次」）→ **不做文字提炼** |
| 两者混合 | 用 VAD 切分，只转语音段 |

> 实测：音乐/排练类文件产出 **100–200 字节**（近乎空）——**符合预期，不是 bug**。

## 五、产物约定（与附件/OCR 统一）

```
~/wechat-export/media-text/<相对路径>.txt    ← 转写文本（与抽文本/OCR 同目录）
~/wechat-export/media-text/.transcribed.tsv  ← 已处理清单（增量用）
```

> **同一个目录放「抽文本 / OCR / 转写」三种产物** —— agent 统一读一处，不用记三套路径。

## 六、决策速查

```
有音频要转写
    │
    ├─ 是微信语音那样的超短片，且每轮只新增几条？
    │      → ✅ 本地小模型(base) + 增量 + 批处理   ← 现状，别改
    │
    └─ 是长音频 / 一次性大批量？
           ├─ 有 ≥8G 显卡 或 能借到 GPU？
           │      → faster-whisper large-v3 + CUDA + VAD（几十分钟）
           ├─ Apple Silicon？
           │      → mlx-whisper + VAD
           └─ 都没有？
                  → ASR API（按分钟计费）或分批慢跑
```

**无论哪条路**：
- 先跑 **VAD** 过滤掉音乐/静音
- **音乐类只记元信息**，不做文字提炼
- 产物统一放 `media-text/`
