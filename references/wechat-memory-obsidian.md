# 微信获取、条件记忆、Obsidian 管理：业务主线规格

## 本 PR 的实际交付状态

已实现：既有解密器的全页认证、恢复覆盖报告和失败退出；导出器的稳定消息 ID、保留旧页面 ID、JSONL 标准事件、明确的解析错误、精确会话/时间/类型筛选，以及分类/项目元数据。原有月度 Markdown 路径和语音转写保留；无法按消息 ID 关联的旧转写单列标注。

样板：`assets/obsidian/memory-management.base` 和 `assets/templates/tpl-memory-control.md` 提供 Obsidian 资料管理字段及三个表格视图。它们没有自动部署到用户 vault。

**未实现：**运行 SQLite、完整受控查询接口、Obsidian 属性回读、自动生成管理页、人机共写镜像器、WAL 恢复与真实微信端到端验证。镜像器写入被平台安全检查拦截，本批没有绕过该限制，也没有提交依赖它的半成品查询实现。现有 `rebuild_chatlogs.py` 保持原样，仍需另行修复；本批筛选是“导出选择”，不是 QKB/Agent 访问权限。旧索引和旧文件不会因修改本轮范围自动撤回。

## 目标与边界

本系统首先解决两件事：在账户持有人明确授权的本机取得微信历史数据；把取得的数据变成按条件可检索、可核对、可持续使用的 Agent 记忆。Obsidian 是第三个面向人的交互面，让用户看见来源、修正分类、控制使用和维护知识。

安全与可靠性应当支撑这条链路，而不是以停掉采集、只保留手工投喂作为最终方案。保留现有采集器、密钥获取与数据库解密能力；只在缺密钥、快照不一致、版本不兼容等情况下明确报障，保留上一份成功结果。

## 一、获取：把“破解”组织成可维护的适配层

这里的破解是账户持有人对自己本机数据库的授权恢复，不是暴力穷举密钥，也不意味着某一种算法可以永久适配所有微信版本。系统应把账号选择、快照、密钥取得、密钥匹配、页面认证、解密、结构解析分开。

建议状态链：

`ACCOUNT_SELECTED → SNAPSHOT_READY → KEY_READY → DECRYPTED → SCHEMA_SUPPORTED → EVENTS_EXPORTED`

每步记录客户端版本、操作系统、账号作用域、数据分片、输入指纹、适配器版本、时间范围、数量及失败原因，不记录明文密钥。不同账号必须独立目录与标识；不能选择第一个账号或仅靠 message_0.db 之类的文件名合并数据。

### 需要解决的问题

- 密钥匹配成功只证明相应加密参数匹配，不代表所有页和所有分片完整。除第一页外，还需验证其他页的认证信息，并在临时文件上检查 SQLite 完整性后才发布产物。
- 正在运行的 SQLite/WCDB 可能把最新提交保存在 WAL 中。仅复制主文件不一定得到完整数据。应优先使用经过验证的应用一致性快照或相应加密驱动的备份能力；不能假定普通 SQLite Backup API 能直接读取加密微信数据库。
- 当前原始页解密器没有 WAL 恢复能力。检测到非空 WAL 必须报告 `WAL_PRESENT`，不能把缺少该部分的结果叫作完整采集。后续单独实现并测试 WAL 恢复适配器，不在这批伪称解决。
- 数据库分片应根据实际文件、表结构和事件时间发现，不把某个 message_N 固定解释为某一年。
- 增量采集与首次回填分别调度。使用消息标识和内容修订去重，采用带重叠窗口的读取和事务检查点，不能只用“最大时间戳”跳过同秒消息或迟到记录。

本批解密改动：全页认证、截断检测、单账号检查、临时校验、原子发布、缺密钥及 WAL 的逐库覆盖报告，以及失败退出。现有密钥获取器没有被删除；没有在真实微信上执行扫描或解密测试。

## 二、记忆：先形成证据模型，再进行语义提炼

Agent 的“学习”首先应理解为检索和使用受控外部记忆，不是自动微调模型，也不是把所有聊天塞进上下文。

### 四类产物及真值

| 层次 | 主要载体 | 内容与作用 |
|---|---|---|
| 原始来源 | 隔离采集目录、原文件 | 加密快照、原附件、解密报告，用户授权后保留；密钥不进入 vault |
| 标准事件 | JSONL，后续可进入本地 SQLite | 账号、会话、消息标识、原始类型、发送者、时间、文本及媒体状态、来源定位与修订 |
| 结构记忆 | 带属性的 Markdown 与实体关系 | 项目、人物、决定、任务、偏好；事实/计划/解释/待确认分开 |
| 可调用上下文 | 带来源的结构化响应 | 按角色、项目、时间、用途、审核状态和预算生成最小必要上下文 |

建议运行 SQLite 保存事件、处理状态、检查点和任务回执；Markdown 保存可由用户修改的知识与使用意图；QKB 是可重建的检索索引，不是知识真值。不能让 SQLite 和 Markdown 同时拥有同一个可编辑字段。

### 事件合同

每条消息至少包含 `schema_version`、`account_id`、`conversation_id`、`message_id`、`event_time`、`sender_id`、`message_type`、`content`、`content_revision`、`source`。

有可靠服务端消息 ID 时优先使用账号+会话+服务端 ID；没有时退回账号+会话+分片+表+本地 ID，并声明该范围。显示名、文件名、时间戳均不能单独充当消息主键。昵称变化不更换实体 ID；未知发送者保持 unknown，不猜成“对方”。

语音转写、图片识别与附件抽取是同一消息的派生产物，携带 `message_id`、原附件哈希、处理模型/版本与状态；不要按相同时间戳把两个片段猜成同一条语音。没有转写的语音应显示“待转写”，不是“没有内容”。

### 条件必须进入执行路径

条件分两层：采集范围决定哪些消息被获取/导入；使用策略决定已有消息是否可以被哪个 Agent 为哪个目的读取。撤销使用授权不等于立刻销毁证据，两者是独立操作。

建议策略包含精确会话 ID 白名单、时间区间、消息类型、排除项、项目/分类、允许角色、是否允许外部模型、默认使用级别。使用级别至少为 `excluded`、`context`、`knowledge`：原始对话可以作为带出处的上下文，但未经确认的推断不能自动升级为已确认事实。

查询路径应为“身份与用途 → 授权范围 → 元数据/实体过滤 → 关键词和向量召回 → 同范围重排 → 必要上下文展开”。过滤要在任何外部模型/嵌入调用前完成；提示词中的“不主动提及”或 frontmatter 标记并不是访问控制。

新事实应使用结构化候选：主体、关系、值、事件有效时间、状态、来源消息、冲突来源和版本。跨会话的人名合并、财务决定、承诺和任务完成等高影响推断进入待确认队列。稳定偏好不按统一三个月删除，项目状态也不能仅因某段聊天较新就覆盖业务权威系统。

## 三、Obsidian：用户能管理，而不只是能浏览

Obsidian vault 是本地 Markdown 文件夹；Bases 在文件属性上建立表格、过滤和分组视图，并非把运行 SQLite “放进 Obsidian”。用户只需理解工作、人物、项目和待处理资料，不需要接触密钥、分片或向量数据库。

推荐双向管理模型：

- **来源层**：机器生成、可追溯的聊天证据与附件链接；用户可阅读，原件不被整理 Agent 改写。
- **知识层**：人物、项目、日记、决策和任务页，按稳定 ID 互链。AI 只更新明确的自动生成区域；用户正文、别名、分类和说明保留。
- **控制层**：用户在属性中管理 category、project、review_status、agent_use、privacy 和归档意图；实际权限不能超过受信配置批准的上限。

主页应提供最近导入、解析失败、待分类、待确认、项目、人物和已排除资料的入口。Bases 与普通 Markdown 页面都能查看，不将社区插件设为强依赖。

### 人机共写规则

不要整页覆盖用户笔记。已有文件被用户修改时，应生成候选更新或只改拥有明确边界的机器区；旧版本归档并校验。新来源不自动推翻用户更正；一个审核决定绑定所审核的来源版本，来源变化后显示“需复核”。用户移走/归档资料后不自动重新创建一个同名副本。

如果用户把 `agent_use` 改为 excluded，下一次受控查询就应停止返回该内容；索引和派生摘要也需要撤销/重建。既有 QKB 和外部 Agent 的直接文件访问不会仅凭这个字段自动受约束，接入前必须验证旁路。

## 本次与后续交付的区分

本批首先落地已有采集/导出链路的可核验性与稳定引用，补业务规格和 Obsidian 可编辑视图样板。它不声称一次完成完整的事件 SQLite、所有微信版本适配、WAL 恢复、多租户访问控制或自动知识图谱。

下一批实施顺序应为：标准事件入 SQLite 与可重试检查点 → 受控上下文接口 → 用户属性回读与审核候选 → 语音/附件按消息 ID 关联 → 更多版本和平台适配。不得先扩大 Agent 数量，再补来源和状态真值。

## 验收矩阵

| 范围 | 必须通过的场景 |
|---|---|
| 获取 | 缺一个分片密钥不可全绿；错误密钥/任意页损坏/截断被识别；非空 WAL 被报告；多个账号不串库；失败不覆盖成功副本 |
| 标准化 | 重复导入幂等；同秒两条消息不合并；昵称变化 ID 不变；未知发送者不臆测；压缩文本失败有原因；附件不可用不被当成空事实 |
| 使用条件 | 项目/日期/角色/用途过滤有效；excluded 不进入上下文或外发；无匹配和服务失败不同；每个结论可定位原消息 |
| 用户管理 | 手动改分类、改别名、排除和归档后保持；AI 更新不覆盖正文；原文和附件链接有效；旧来源版本仍可核对 |
| 全链路 | 在独立授权样本上完成采集→事件→分类→Obsidian→Agent 回答，再报告真正可用，而不是仅以命令退出 0 验收 |

## 本批代码如何试验

先在独立的授权样本目录试验，不覆盖现用微信或知识库。已有采集与密钥获取按现有适配器执行；本 PR 没有新增绕过系统授权或通用版本破解方式。

```bash
# 把 example 中的账号、会话 ID 和日期换成真实授权范围
python3 assets/scripts/collector/export_searchable.py \
  --work /absolute/path/to/sample-wx-export \
  --policy /absolute/path/to/export-policy.json
```

策略结构见 `assets/export-policy.example.json`。也可通过 `WX_EXPORT_POLICY` 指定策略供原刷新脚本调用。不要把 account_id 当作认证：它是使用者配置的稳定数据命名空间，每个账号必须使用独立 work 目录。

产物位于 `searchable/`：旧格式 `<会话>/<YYYY-MM>.md` 继续保留；`_events.jsonl` 提供标准事件；`_export-report.json` 记录本次范围、消息数、来源页哈希和错误；`_page-map.json` 将账号/会话/月绑定到首次使用的页面路径，使昵称变化不再新建重复页面。升级和迁移应保留这份路径注册表。每条事件的 evidence_ref 指向计划镜像后的原文消息块；镜像完成前它只是目标引用，不表示最终 vault 中已存在该页。显示时间继续采用采集机本地时区以兼容旧链路，JSONL 的 event_time 为带时区的 UTC，timestamp 为 Unix 秒。

`recovery-manifest.json` 的 READY 仅表示这次实际枚举的快照文件通过检查，不能证明遗漏的历史分片从未存在，或最新客户端数据已经全部进入快照。`_export-report.json` 不是整个文件夹的清单：旧范围的页面保留，不能把目录里所有文件无条件交给 Agent。

原导出形式不带 --policy 时，继续使用关注名单。旧 id 能读取时保留；新页面和消息用稳定 ID。名称相同导致路径冲突时显式报错，需指定不同导出名称。没有可靠 server_id/local_id 时，回退标识会在 id_scope 中说明局限。

现有 `rebuild_chatlogs.py` 会重写页头且仍有清理逻辑，本批没有修改它。因此分类/项目元数据应从新的 JSONL 或导出页读取，不能假定旧镜像器已把这些字段完整传入最终 vault。现有 raw 镜像、QKB 和所有下游索引必须另行验收后才能启用无人值守。

Obsidian 样板可在独立测试 vault 中查看：将 `.base` 样板放入 vault，以管理卡模板建立 `wiki/memory-controls/` 下的页面，再用 Bases 查看属性。这个操作不连接 SQLite、不配置权限，也不自动同步用户修改回 Agent。

升级时将 collector 下的 `wxexport/crypto.py`、`decrypt.py`、`__main__.py`、`refresh.sh`、`export_searchable.py` 成套更新并先验收，不能只替换一个文件。当前仍是单写入者、逐文件发布；不声称有跨文件事务、跨机互斥或全量高性能回填。

离线测试依赖在 `tests/requirements.txt`；测试入口为 `python3 -m unittest discover -s tests -v`。合成密文测试验证指定参数下的页面认证行为，SQLite 测试验证结构与覆盖报告；它们不是独立的真实微信版本兼容性证明。

## 技术依据

- SQLite WAL：<https://sqlite.org/wal.html>，已提交事务可能仍存在 WAL 中，WAL 模式不适合跨主机网络文件系统。
- SQLite Backup API：<https://sqlite.org/backup.html>，备份需要可正确打开来源的数据库连接；并不自动解决第三方加密格式。
- Obsidian 数据存储：<https://help.obsidian.md/data-storage>，vault 中的本地 Markdown 是笔记载体。
- Obsidian Bases：<https://help.obsidian.md/bases> 与 <https://help.obsidian.md/bases/syntax>，视图基于本地文件及属性。

以上资料用于设计依据；实际微信版本、系统权限、模型效果和 Obsidian 界面仍需目标环境验证。
