# SETUP · 明确授权后的部署流程

本文件只在用户明确要求安装、初始化、升级或修复环境时执行。普通查询、审阅、第一条消息或意图不明的“开始”都不授权部署。已有知识库不重复初始化。

先读 `references/review-fixes.md`，了解本版限制与旧安装的迁移方式。按需读取各平台参考手册，不能把历史实测经验当作当前兼容性保证。

## 第 0 步：确认环境与已有状态

在用户明确授权后运行 `bash setup/detect.sh`、`bash setup/detect-agent.sh`，读取已有 state.json 与配置。环境探测只作为事实线索，不授权安装依赖或启动任务。当前核心受限执行器使用 POSIX 文件接口，需要 macOS/Linux 与 Python 3.9+；原生 Windows 不作为已完成安全验收的平台。

区分“本机已有框架”和“本轮授权使用哪个框架”。外部 Agent 的工作区与系统权限要单独设定，不能因为发现 CLI 就自动切过去执行。

## 第 1 步：建骨架或接入已有库

确认用户指定的 vault 路径、数据用途与主要领域，使用绝对路径或 `~/...`。新库可运行：

```bash
bash setup/init-vault.sh "<用户指定的知识库路径>"
```

已有库先备份并检查结构，只补缺，不覆盖用户资料。配置中的 `vault` 与 QKB 的 `config.toml` 必须指向同一目录；初始化模板后应逐项核对。

检查根目录说明、raw、wiki、templates 和 id/context/created 页头。记下该步骤的实际状态，不因目录存在就写“内容初始化完成”。

## 第 2 步：配置模型与检索

确认用户允许哪些数据发送到哪些服务。用 `assets/config.json` 作为配置结构参考，配置文件由 `SHUZI_CONFIG` 指定，默认在 `~/.shuzi-rensheng/config.json`。

API 使用 `api.llm`、`api.embedding`、`api.vlm` 分段。凭据仅由配置指定的环境变量读取，不放入知识页、命令行参数、版本库或生成的定时文件；不要要求用户把完整凭据发进对话。

内置 API 只提供受限文件工具，没有命令执行、通知、账本转换或索引工具。选择该后端时必须将这些步骤保留给确定性管线。外部框架需要独立沙箱。Ollama 旧适配器尚无完整文件工具循环，本版本明确返回不支持，而不是把文本生成当作整理成功。

QKB 是外部依赖，配置与版本需要核实。小规模验证关键词、向量和重排行为，再扩展数据量。没有 QKB 时可先使用纯 Markdown 浏览，但不能宣称语义检索已可用。

本地模型按实际内存、吞吐、批量规模和质量测试选择，不把单一显存数字当作通用硬门槛。不启用用户未批准的付费调用或大批量回填。

## 第 3 步：连接授权数据源

从少量非敏感手工资料开始更易验证。微信、邮件、聊天、语音等数据源必须逐个确认范围和采集机器；系统权限、应用兼容性与数据处理授权分别核对。

原始证据只新增保留；AI 整理写入 wiki。用户数据可能包含第三方资料，不能因能够读取就全部导入或外发。private 与共享资料应使用隔离的索引/服务权限，本包的输出过滤不替代后端隔离。

需要多机时再阅读 `references/network-setup.md`，使用用户自己的网络与主机配置。不自行扩大远程访问权限。采集和旧媒体脚本需独立验收，启动中继不等于导出成功。

## 第 4 步：配置通知（可跳过）

仅在用户明确选择渠道和收件范围后配置。通知内容不得夹带私密资料或凭据；测试发送也需要在已授权范围内。未接通通知时明确标记，不用日志写入代替“用户已收到”。

## 第 5 步：定时任务（明确选装）

先预览指定任务：

```bash
bash setup/schedule.sh qkb-follow lint --dry-run
```

必须明确列出任务名；无参数不会自动安装推荐集。确认机器本地时区、路径、运行用户、数据外发与模型后端，再将 `schedule.enabled` 设为 true，运行不带 `--dry-run` 的同一命令。

任务名包括 chat-ingest、finance-ingest、rebuild、transcribe、lint、idea-review、rollup、qkb-follow、collector-refresh。只选择本机实际可运行且已验收的项目；不用 all 代替逐项检查。

AI 定时任务使用 `schedule.engine` 指定后端，默认 api；不能采用 auto、manual、ollama。服务运行环境需要独立提供所需环境变量，交互式 shell 的设置不保证 launchd/cron 可见。定时器不复制凭据。

macOS/Linux 都通过 `setup/schedule.py` 生成。Linux 只更新本包具名区块，保留其他 cron；旧无标记条目要先人工确认停用，避免重复运行。不要调用旧原生 Windows 安装器绕过平台限制。

修改时间、vault 路径或 Python 环境后重新生成相关任务。关闭 `schedule.enabled` 会阻止使用新包装器的后续任务，但不终止已有进程或旧独立调度。

## 第 6 步：区分骨架验收与真实链路验收

```bash
bash engine/run.sh --list
bash engine/run.sh lint --dry-run
```

以上只验证参数和提示词生成，不调用模型、不证明笔记正确。对配置、目录、依赖、权限和定时注册分别记录结果；未配置的项目标记“未配置”，不是失败或通过。

真实链路另用小型授权样本验证：原文保留、目标笔记存在且格式正确、内容有出处、索引运行成功、检索可命中并回到原文。`EXECUTED_UNVERIFIED` 只表示引擎退出正常，不等于业务 PASS。

## 第 7 步：首次回填（可跳过，另行批准）

先抽样评估质量、数据量、资源及费用，并说明将读取、写入和外发什么。只有用户明确批准后才执行。不要以“已启动”作为完成回执；只有可用的调度或执行器确实接管时才能报告任务已提交。

批量任务必须有输入/成功/失败清单，失败可重试，原件与已有页面有备份。部分完成如实报告，不能因为某个任务正常退出就宣称整库就绪。更多设计参考 `references/bootstrap.md`，其历史命令与性能估计需按当前环境复核。
