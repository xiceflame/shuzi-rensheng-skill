# SETUP —— 从零开始，一步步建起这套系统

> **给 AI agent 的指令**：用户第一次用这个 skill（说「开始」或发第一条消息）时，
> **不要直接开始整理内容**。先按本文件走一遍 setup。
>
> **怎么走**：
> 1. 先跑 `bash setup/detect.sh`（探测环境，输出 JSON）
> 2. 读 `~/.shuzi-rensheng/state.json`（若存在）看做到哪一步了
> 3. **只做没做完的步骤**；每完成一步就更新 `state.json`
> 4. 每步都**先解释「这步在干嘛、为什么」**，再问用户要输入（不要一次性问一堆）
> 5. 用户可以随时说「跳过」「稍后再说」——**除了第 1 步，其余都能跳**
>
> **语气**：像帮朋友装机，别像念手册。一次只推进一件事。

---

## 总览：8 步（第 0~7 步）

| 步 | 做什么 | 必需？ | 耗时 |
|---|---|---|---|
| **0** | 环境 + Agent 自我识别 | 自动 | 秒 |
| **1** | 建知识库骨架 | ✅ **必需** | 1 分钟 |
| **2** | 定性能架构 + 配 API（三类） | ⭕ | 2 分钟 |
| **3** | 配采集端（多机含组网）+ 首次全量导出 | ⭕ | 5–30 分钟 |
| **4** | 配提醒渠道 | ⭕ | 1 分钟 |
| **5** | 配定时（日常增量） | ⭕ | 1 分钟 |
| **6** | 验收（骨架就绪） | ✅ **必需** | 1 分钟 |
| **7** | ★★ **启动首次初始化**（估算→确认→后台跑） | ⭕ | **几小时级** |

> ⭐ **第 7 步放最后是有意的**：它最漫长。**发起后用户就能去干别的**，
> 不用等它跑完再做别的设置。发起即结束。
>
> **只做第 1 + 6 步也能用**（空知识库，手工投喂）。
> 但**没有第 7 步，系统就没内容** —— 它是「从空库到有内容」的关键。
>
> **第 7 步开始前必须先跑 `setup/estimate.sh` 给用户「时长 + 成本」估算**，确认后再启动。


> **只做第 1 + 7 步也能用**：得到一个空知识库，你可以手动往里放东西、让 agent 整理。
>
> ⭐ **第 4 步是「从空库到有内容」的关键一步**，也是**唯一必须借算力（API/GPU）**的一步。
> 它**只做一次**，之后靠日常增量维护。详见 `references/bootstrap.md`。

## 第 0 步 · **先搞清楚「我在哪、我是谁」**（自动，不用问用户）

> **这一步必须先做。** setup 的后续步骤**取决于你（AI）跑在什么框架里** ——
> 不同框架的**工具名、定时方式、通知渠道、工作区约定全都不一样**。

### 0a · 机器环境

```bash
bash setup/detect.sh
```

输出：操作系统、Python/Node/Ollama、GPU、微信容器、Obsidian、已有 vault。

### 0b · ★ **Agent 自我识别**（新增，最关键）

```bash
bash setup/detect-agent.sh
```

输出 JSON：**你是哪个框架**（openclaw / claude-code / cursor / codex / hermes / api-only / generic）、
你的**能力边界**（能不能跑命令、能不能系统定时、能不能远程执行）、以及**适配建议**。

**然后必须读你自己的适配说明**：

```
setup/frameworks/<你的框架>.md
```

里面写清了：你该用什么**工具名**、任务怎么跑、定时放哪、通知怎么发、技能怎么装。

> ⚠️ **为什么要这一步**：
> - OpenClaw 用 `exec(host=node)`，Claude Code 用 `Bash` —— 工具名不同
> - OpenClaw 有 cron，Claude Code 没有 → **定时必须落到系统层**
> - 有人用 Discord，有人用飞书 —— **通知渠道不能假设**
>
> **框架识别错了，后面每一步都会用错工具。**

**根据结果决定后面几步怎么走**：
- `os=windows` → 采集走 `references/windows-collector.md`（免权限）
- `os=macos` + 有微信 → 采集走 `references/wechat-pipeline.md`（要 FDA/中继）
- `has_ollama=false` 且用户不想装 → 第 2 步必须配 API
- `has_gpu=false` → 嵌入建议走 API（本地 CPU 慢）

## 第 2 步 · 先看性能，再定「什么本地跑 / 什么走 API」

> ⚠️ **这一步的决策依据是第 0 步的 `gpu_tier`**，别拍脑袋。

### 2.1 核心原则：**增量与批量分开**

| | 增量（日常） | 批量（首次回填） |
|---|---|---|
| 数据量 | 每天几十~几百条 | 几万~几十万条 |
| **怎么跑** | ✅ **本地长时间运行** | ⚠️ **必须用 API 或高性能 GPU** |
| 弱机器 | 完全够用 | ❌ 几小时 → **几天** |

**详见 `references/performance-tiering.md`。**

### 2.2 按 `gpu_tier` 决定分工

| gpu_tier | 显存 | 本地能跑 | 必须走 API |
|---|---|---|---|
| **xl** | ≥20GB | 嵌入 + 重排 + 语音 + 7B 量化 | 大 LLM / VLM |
| **lg** | ≥12GB | 嵌入 + 重排 + 语音 | 大 LLM / VLM |
| **md** | **≥8GB** ✅ **门槛线** | 嵌入 + 重排 + 语音 | 大 LLM / VLM |
| **sm** | <8GB | ❌ **不够** | **全部** |
| **无独显** | — | ❌ **不够** | **全部** |

> ⭐ **硬门槛：8GB 显存**（用户拍板）。
> **≥ 8GB** → 可以本地跑嵌入/重排/语音；**< 8GB** → **一律走 API**，本地只跑纯脚本。
> **大 LLM 与 VLM 一律走 API** —— 本地量化小模型质量掉得厉害，且拖慢整机。
>
> 详见 `references/gpu-requirements.md` 与 `references/performance-tiering.md`。

### 2.3 配 API（可选，但建议）

> **先跟用户说清楚**：
> 「这套系统大部分活儿是本地算的（解密、转码、建索引），**只有『把聊天记录提炼成笔记』需要大模型**。
> 大模型建议**用 API**（省事、便宜、不用装东西）。」
>
> **首推 DeepSeek V4.1 Flash**：中文强、**有峰谷价**（空闲时段半价）、便宜。

---

### 2.4 三类 API 的配置（具体填什么）

**目的**：让「整理」「看图」「语音转写」「向量检索」能跑起来。

> **先跟用户说清楚**：
> 「这套系统大部分活儿是本地算的（解密、转码、建索引），**只有『把聊天记录提炼成笔记』需要 AI**。
> 你有两种选择：**用 API**（省事、便宜、不用装东西）或**全本地**（免费但要装模型）。
> 也能混着来。」

**三类 API（全部走 OpenAI 兼容协议，不绑厂商）**：

| 类型 | 用途 | 不配的后果 |
|---|---|---|
| **LLM** | 提炼笔记、写日记/人物页 | ❌ 整理任务跑不了（可人工兜底） |
| **Embedding** | 向量检索 | ⭕ 检索退化为关键词匹配 |
| **VLM** | 看图（打勾表/日程表/截图） | ⭕ 图片内容读不了 |

**引导用户填**（逐类问，能跳就跳）：
```
LLM：  base_url（如 https://api.openai.com/v1）+ api_key + model
Embedding：base_url + api_key + model + dimension
VLM：  base_url + api_key + model
```

> 国内常用兼容端点（都可直接填 `base_url`）：
> DeepSeek / 智谱 / 通义 / 硅基流动 / 月之暗面 / 本地 vLLM。
> **统一用 OpenAI 协议，不用 Anthropic 的格式。**

**写配置**：把结果写进 `~/.shuzi-rensheng/config.json` 的 `api` 段（模板见 `assets/config.json`）。
**API key 不写进 JSON**，而是让用户 `export XXX_API_KEY=...`（写进 shell profile），JSON 里只存**环境变量名**。

**若用户选「全本地」**：
- 语音 / 文档抽取 / OCR → **`bash setup/local-models.sh` 一键装齐本机模型**
  （Apple Silicon 自动选 mlx-whisper，其他平台 faster-whisper；macOS 用系统 Vision OCR，
  Linux/Windows 用 RapidOCR；`--ollama` 追加本地嵌入、`--mineru` 本机跑 PDF）
- 嵌入 → 本机 Ollama + `qwen3-embedding:4b`（见 `references/embedding-setup.md`）
- LLM → 本机 Ollama（质量有限）或「没有 agent 就用 `engine/run.sh --engine manual` 人工贴」

**怎么验证**：
```bash
bash engine/run.sh --list                 # 能列出任务
bash engine/run.sh lint --dry-run         # 能拼出 prompt
curl -s "$LLM_BASE_URL/models" -H "Authorization: Bearer $LLM_API_KEY" | head -c 100
```

### 3.B 多机组网（仅「采集机与大脑分离」时做；单机跳过）

**先判断形态**：
- **单机**（采集与大脑同一台机器，大多数用户）→ **什么都不用做**。
  `config.json` 的 `network.topology` 保持 `single`，采集脚本自动跳过跨机推送。
- **多机**（如 MacBook 采集、台式机/服务器当大脑，或另有 GPU 机跑嵌入/重排/OCR）→
  走 **`references/network-setup.md`**：用**你自己的 Tailscale 账号**把几台机器组成一个
  私有内网（零公网暴露），再把主机名填进 `config.json` 的 `network` 段。

> 🔧 组网中的「装 Tailscale 客户端 + 登录账号」**必须人工**（图形界面授权，每台一次），
> 其余（ssh 免密、目录准备、连通性验证）agent 可代跑。

**问用户**（仅多机）：
> 「采集和整理是同一台机器吗？分开的话，几台机器分别是什么？」
> —— 据此写 `config.json` 的 `network` 段（brain.host / gpu.host），并用 network-setup.md §6 验证连通。

**问关注名单**（若接了微信）：
> 「你最在意哪些人/群的消息？说名字就行，我会写成关注名单。」
> —— 写入 `focus.txt`（模板见 `assets/templates/focus.txt.template`，**精确匹配**）

**怎么验证（试跑，不是全量）**：
> ⚠️ **本步只做「小规模试跑」验证管路通**（跑一次增量 refresh，确认密钥能拿到、
> 有产物产出即可）。**首次全量导出放到第 7 步**，跟解密一起、有人盯着做。

**写 state**：`{"step3": {"done": true, "platform": "<windows|macos|none>", "network": "<single|multi>"}}`

> 然后告诉用户：「**骨架搭好了，管路也通了。最后一步是把你的历史数据灌进去——
> 那一步最花时间，我们放到最后启动，启动完你就可以去干别的。**」

## 第 7 步 · ★★ 启动首次初始化（回填 + 建图谱）（**放最后**）

> **放最后是有意的**：这一步**最漫长**（几小时级）。
> 让它**在最后启动**，用户**发起后就能去干别的** ——
> 不需要等它跑完再回来做别的设置。
>
> **发起前必须先估算、让用户确认**（见 7.0）。完整说明见 `references/bootstrap.md`。

### 7.0 ★ 先让用户「用语言阐述关注点」

**不要机械按全量算** —— 先问清楚，范围往往能缩小一个数量级。

**问用户（用自然语言，不用填表）**：

> 「在开始导入前，先跟我说说：
> ① **关注的会话** —— 哪些人/群的对话你要？说名字就行
> ② **关注的方向** —— 工作？家庭？某个项目？健康？
> ③ **截止到什么时候** —— 只看近一年？还是全部都要？」

**为什么要问**：用户的回答**直接决定估算**。
> 实测：全量（28 会话 / 3 年）≈ **7.5 小时**；
> 但若只看 **8 个会话、近 12 个月** → **13 分钟**。**差 35 倍。**

**把阐述结果落到三个产物**：
1. **`focus.txt`**（若第 3 步没填）—— 把用户说的会话名写进去（**精确匹配**）
2. **`--convs N`**（估算用：会话数）
3. **`--months N`**（估算用：时间范围，或"全部"）

### 7.1 ★ 据此估算「要多久、多少钱」

```bash
# 按用户阐述的范围估（不是全量）
bash setup/estimate.sh --convs 8 --months 12 --parallel 4
```

**⚠️ 启动前必做** —— 让用户**知情**。

```bash
bash setup/estimate.sh
```

它会盘点实际数据量，输出：

| 输出 | 例 |
|---|---|
| 数据盘点 | 2266 会话 / 66.7 万条消息 / 7565 条语音 / 1294 份附件 |
| **时长估算** | 慢路线（全本地）**15.9 小时** ｜ 快路线（GPU+API）**8.8 小时** |
| **成本估算** | LLM 提炼 ≈ ¥2–4（空闲/高峰）｜ 语音 ASR ≈ ¥21 ｜ 嵌入 ≈ ¥0.1 |
| 建议 | 「预计 8.8 小时 —— **建议启动后去干别的**」 |

**拿这个结果问用户**：
> 「这套初始化预计 **X 小时**、一次性约 **¥Y**。
>  ① 现在启动？（我会放后台，**你可以去干别的**，完成了会通知你）
>  ② 还是先只做阶段①（免费部分），之后再决定？」

### 7.2 先跟用户把话说清楚

> ⚠️ 「接下来要处理**过去 N 个月的全部历史数据**，这是**一次性大批量任务**：
> - 用这台机器本地跑，可能要 **几小时到几天**
> - 建议用 **API** 或**借一台 GPU 机器**跑完再回来
> - 费用是一次性的（见 `cost.md`），之后日常只花很少
>
> **要现在做，还是先跳过、以后再回填？**」

### 7.3 数据从哪来

| 来源 | 怎么进系统 |
|---|---|
| **微信**（首次必然要接） | 采集端**全量导出** → `~/wechat-export/`（见第 3 步） |
| **Work Buddy / 其他桌面工作端** | 能导出就导出成文件 → 丢进 `<vault>/raw/` |
| 邮件 / Notion / 手工资料 | 同上：**变成文件 → 进同一套流水线** |
| Claude / ChatGPT 导出 | `raw/chat/claude/` · `raw/chat/chatgpt/` |

> 🔑 **关键**：只要变成**文件**，就进了同一套流水线——**不需要为每个数据源单独设计**。

### 7.4 ★ 解密与导入阶段 —— **必须有人盯着**

> ⚠️ **微信破解这一段不能启动后就走人。** 它可能出各种问题
> （密钥拿不到、微信崩了、某分片缺失、权限被拒…）——
> **每一种都有补救方案，但需要人在场判断**。

**必须盯着的原因**：
| 可能出的事 | 现象 | 补救 |
|---|---|---|
| 密钥扫描不到 | 「密钥 0 个」 | 确认微信在运行且已登录；重跑只读扫描 |
| 微信崩溃 | 微信闪退 | 别用 lldb 断点（本就会崩）；重启重来 |
| 某分片缺密钥 | **某段时间整段没消息** | 按分片年表排查，单独补扫 |
| 权限被拒 | `Operation not permitted` | 检查 FDA / Terminal 中继 |
| 触发授权弹窗 | 卡住等点击 | 走 Terminal 中继，人点一下 |

**所以对用户说**：
> 「**解密这段我在盯着**，可能中途需要你配合（点个授权、重启下微信）。
> 我出问题会立刻告诉你，每种情况都有补救方案，不用慌。
> 等**解密完成、数据落到盘上**之后，后面的回填就不需要你守着了。」

**解密完成的标志**：`~/wechat-export/` 下各目录都有产物（见 `wechat-pipeline.md`）。

### 7.4.1 ★ 首次全量导出命令清单（按序执行）

> 首次 ≠ 日常增量。**两个脚本都要跑，顺序如下**：

| 序 | 命令 | 作用 | 产出 |
|---|---|---|---|
| 1 | `bash ~/.wxexport/refresh.sh` | **主刷新**（首跑即含近 3 年 searchable + 近 1 年语音） | focus/ · focus-voice/ · focus-images/ · focus-media/ · focus-money/ · searchable/ |
| 2 | `bash ~/.wxexport/full_refresh.sh` | **全部历史**（全量渲染 2266 会话） | text/（2018 至今） |
| 3 | 确认产物齐全 | `ls ~/wechat-export/` | 各目录非空 |

> ⚠️ **只跑 full_refresh.sh 不够**——它只产 text/（全量文字）；
> 语音/图片/附件/财务/检索版要靠 refresh.sh。
> 首次之后，这两个脚本分别挂定时（refresh 每 4h / full 每周）。

### 7.5 ★ 回填与建库 —— 可以离开，**支持并发**

**解密完成之后**，剩下的回填是**可并发、可无人值守**的：

| 环节 | 并发方式 | 提速 |
|---|---|---|
| **向量嵌入** | **API 异步并发**（批量提交，不等一条回一条） | 数倍 |
| **LLM 提炼** | **每个 agent / thread 处理一个月** | 数倍 |
| 语音转写 | 按文件多进程 + GPU | 几十倍 |

**LLM 提炼的并发分片建议**：
```
thread 1 → 2025-01 的全部会话
thread 2 → 2025-02
thread 3 → 2025-03
…
```
> 每月独立成片，**互不干扰**；写不同月份的文件，**不会冲突**。

**告诉用户**：
> 「解密完了，接下来是回填（预计 X 小时）。**这段你可以去干别的**，
> 完成后我通知你。」

### 7.6 四个阶段（按算力需求递增，逐段报进度）

| 阶段 | 做什么 | 算力 | 成本 |
|---|---|---|---|
| **① 本地免费** | 去重 · 抽文本 · 本地 OCR · 短片转写 · 解密 · 图片解码 | 任意机器 | **0** |
| **② 需算力** | 长音频转写（faster-whisper+VAD）· 全量向量嵌入 | GPU 或 API | 低 |
| **③ 需大 LLM** | **把原始数据提炼成知识库页面** | **必须 API** | **主要花费** |
| **④ 建图谱** | 补内链 · 修孤岛 · 建汇总层 · 重建索引 | 本地 | **0** |

> ✅ **先把阶段①免费的全做完** —— 能省掉后面一大半 API 用量。
> ⚠️ **阶段③最慢也最贵**，务必分批量、报进度、**排在空闲时段**（峰谷价差一半）。
