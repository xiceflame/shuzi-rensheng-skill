# DeepFill · 历史回填 / 深度挖掘

> **目标**：把 `raw/chatlogs/` 里的**历史原始记录**整理成结构化知识
> （「我的每一天」日记 + 人物时间线 + 月/季汇总），并入库可检索。
> **日常增量别用本技能**（数据更新由 chat-ingest 每 4h 自动处理）；
> 本技能只管「**历史欠账**」和「**按需深挖**」。

## 一、什么时候用（触发）

- **回填**：「整理 2025 年 3 月的聊天」「把 2024 年的记录灌进去」「继续往前推一批」
- **深挖**：「把 A 在过去所有聊天里的痕迹整理出来」「围绕 XX 项目把历史聊过的一切汇总」
- **补缺**：「XX 月的日记还没建」「2025-Q3 季汇总缺」

## 二、动手前：先摸底（**必做，别上来就跑**）

```bash
# ① 数据盘点：范围里每个月有几个会话、多少天活跃
for m in 2025-03 2025-04 2025-05; do
  echo -n "$m: $(ls ~/wechat-export/../../数字人生/raw/chatlogs/*/$m.md 2>/dev/null | wc -l) 会话, \
活跃 $(grep -rhoE "^\[$m-[0-9]{2}" ~/数字人生/raw/chatlogs/*/$m.md 2>/dev/null | sort -u | wc -l) 天"
done
# ② 已有覆盖：wiki/journal/ 现有月份（别重复建）
ls ~/数字人生/wiki/journal/ | grep -oE '20[0-9]{2}-[0-9]{2}' | sort -u
# ③ 量级 → 成本/时长（每 ~7200 消息/月 ≈ 40–110 万 tokens 源内容；
#    子代理 1 个月/个，实测 4–14 分钟/个；嵌入 4090 ≈ 45 分钟/万 chunk）
```

**和主人确认**：范围、批次（默认 3 个月/批）、要不要人物时间线与月/季汇总。

## 三、模式 A · 增量回填（按日期，3 个月一批）

**已验证的执行法**：**每个月一个子代理并行**，只允许它新建 journal 页，别的都不碰。

1. **派批**（提示词模板见 `references/playbook.md` §1）：源 `raw/chatlogs/<会话>/<YYYY-MM>.md`，
   逐日生成 `wiki/journal/YYYY-MM-DD.md`
2. **校验**：覆盖天数对得上、`id` 无重复、断链=0（脚本扫 `[[..]]`）
3. **人物时间线**（`references/playbook.md` §2）：按人 grep 日记 → 增量插入时间线（**只增不改**）
4. **月/季汇总**（`references/playbook.md` §3）：`wiki/monthly/`、`wiki/quarterly/`
5. **镜像 + 索引**：`media_text_to_vault.py` → `qkb-lock.py ingest` → 大批量 embed 走 4090
   （`qkb-bigjob embed`；**避开 MinerU 批**，GPU 会抢）
6. **双维护**：`index.md`（月/季入口、journal 覆盖数）+ `log.md`

> ⚠️ 每批做完**给主人抽查**（抽 2–3 天），确认格式再继续下一批。

## 四、模式 B · 深度挖掘（按人 / 按主题）

1. **定关键词**：人名 + 全部别名（如 张三=San Zhang/张老师）、主题词（如「报价」「恰空」）
2. **跨全库扫**：`raw/chatlogs/*/*.md` 全月份范围 grep（注意别名变体、错别字）
3. **产出**：
   - 更新 `people/<姓名>.md`「时间线（事件+意义）」（每条链 `[[日记日期]]`·`[[项目]]`）
   - 新发现的人 → 按 `tpl-person.md` 建页；**建页 ≠ 完事**：必须同步 **人物索引登记 + log.md 记录**
     （实测教训：曾有一轮 dream-person 挖出新联系人，页建了但索引漏更新、log 没记 → 下游以为还没建档）
   - 按写入边界：若本轮 agent 无 people/ 写权 → 只出报告 + 回写台账，由 owner 落库
   - 主题 → 归到对应项目页「历史材料」，或建 `wiki/tasks/<slug>.md`
4. **防幻觉**：拿不准标「待确认」；**发言人未标注不臆测**；金额标「待对账单确认」

## 四·B 置信度分级 + 关系维护（每轮必做）

**① 置信度分级入库**——每条发现标 高/中/低：

| 置信度 | 处理 |
|---|---|
| **高**（多源互证/主人确认/记录明确） | 直接写入对应页 |
| **中**（单源、细节存疑） | 写入但标「待确认」 |
| **低**（猜测、孤证、含混） | **不落库**，改写成问题进台账「**待问主人**」 |

**② 关系维护视角**——挖掘时**有意扫「维护时机」**：
生日 / 纪念日 / 比赛演出节点 / 生病康复 / **与我久未联系 >90 天** / 我欠对方的承诺。
发现即登记台账「关系维护时机」（对象 + 建议动作 + 日期）——**挖信息的同时主动经营关系**。

## 四·C 嵌入策略（大量新 chunk → **唤醒 4090**）

回填/深挖会产生大量新页 → 大量待嵌 chunk。**决策规则**：

| 场景 | 做法 |
|---|---|
| 日常增量（pending ≤ 200） | **什么都不用做**——常驻守护 `qkb-follow`（每 5 分钟）自动消化 |
| 批量回填（pending > 200 / 半年起） | **唤醒 4090**：`qkb-bigjob embed`（一行命令，见下） |

```bash
# 方式一（推荐，自动排队+自动休眠）：把作业排进 GPU 队列
mkdir -p ~/wechat-export/gpu-queue/pending
echo '/usr/bin/python3 ~/.config/qkb/qkb-bigjob embed'   > ~/wechat-export/gpu-queue/pending/embed-$(date +%s).job
# 调度器（com.<你的用户名>.gpu-scheduler，每 2 分钟）会：唤醒 4090 → 串行执行 → 完成后闲置 15 分钟自动休眠

# 方式二（4090 已在醒着时）：直接跑
/usr/bin/python3 ~/.config/qkb/qkb-bigjob embed      # 自动：置 prefer-4090 标记 → embed-proxy 路由到 4090
                                                     # 结束自动清标记；4090 离线自动回落本机
```

- **实测速度**：4090 ≈ 0.08–0.25 秒/chunk；本机 M4 ≈ 4 秒/chunk（**16 倍差距**）
- **量级参考**：1 个月 journal ≈ 200–400 chunks；**半年回填 ≈ 1.5–2.5k chunks**（4090 约 5–10 分钟）；
  22 个月全欠账 ≈ 4–9k chunks（4090 约 20–40 分钟）
- **双保险**：就算忘记手动唤醒，`qkb-follow` 检测 pending > 200 也会**自动切 4090**
- ⚠️ **别与 MinerU 批同时跑**（抢 GPU，曾导致嵌入进程挂死）——先确认 MinerU 批结束
- 嵌入期间**检索不中断**（向量逐块可见，关键词检索始终可用）

## 五、硬规则（与 shuzi-rensheng 相同，违者返工）

1. **只新建/增量**：已有内容不删不改；时间线按日期插入
2. **四类区分**：事实 / 计划（未落实）/ 意义（解读，措辞保守）/ 待确认
3. **人名带别名 + 跨会话推断**；**发言人未标注不臆测**
4. **链接**：`[[人名]]`/`[[项目]]` 必须已存在，**勿造断链**；
   chatlog 用路径式 `[[raw/chatlogs/<会话>/<YYYY-MM>|YYYY-MM]]`
5. **frontmatter 三件套**：id（uuid，**不重复**）+ context + created
6. **过滤噪音**：`[表情]`/`[系统]`/单条 `[链接/文件]`；**不编造**，没内容就写「无」
7. **嵌入大批量走 4090**（`qkb-bigjob embed`，本机 4s/chunk 会跑 40 小时）

## 六、验收清单

- [ ] journal 覆盖天数 = 数据活跃天数（无缺日）
- [ ] 全部 `id` 唯一；断链 = 0
- [ ] 人物时间线已更新且与日记互链
- [ ] 月/季汇总齐（缺的上一个月数据就说明原因）
- [ ] `qkb status` pending=0；`vaultq "<当月事件>"` 能召回
- [ ] `index.md`/`log.md` 已更新
